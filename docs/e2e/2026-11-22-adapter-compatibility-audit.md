# Hermes and OpenClaw adapter audit — 2026-11-22

Qubit has three usable compatibility paths with different contracts. Hermes Python plugins can share the existing Qubit import and registration surface. Portable Agent Plugins can contribute skills and MCP descriptions. The OpenClaw migration can translate supported user data and settings. An OpenClaw JavaScript plugin identified by its manifest still requires a compatible runtime for its SDK registrations.

## How to extend the adapters

1. Preserve one Qubit install and registration path. Decode each foreign format into a reviewed install plan listing skills, tool names, hooks, MCP transports, permissions, prerequisites, and the exact upstream version. Show discovery, validated import, activation and invocation separately. Capture unknown fields for inspection and refuse to activate any plan with untranslatable authority or credential rules.
2. Expand portable coverage first. Pin representative Agent Plugins bundles and older Hermes Python plugins. Verify manifest and skill parsing, version negotiation, resource paths, and an actual tool call on each supported transport. Keep `stdio`, legacy SSE and Streamable HTTP separate in the test matrix. Test OAuth and secret references with disposable credentials and a named local or approved test endpoint.
3. For native OpenClaw SDK plugins, implement an explicitly versioned Node host behind Qubit's existing broker and approval pipeline. Start with one capability, such as tool registration and invocation. Run source unchanged in an isolated process with explicit filesystem and network grants. Capture tool schemas and map calls and cancellation onto Qubit's existing registry. Add lifecycle hooks or channels only when there is an end-to-end contract and test for each. Keep the original SDK API version as part of the installed artifact metadata.
4. Translate skill prerequisites before enabling imported skills. Record the source directory, pin, requested binaries, environment names, tool dependencies and eligibility rules. Apply Qubit's existing discovery and approval gates. Report unavailable dependencies and source-specific tools with a typed diagnostic. Use explicit alias mappings for tools whose names changed, backed by argument and result-schema tests.
5. Exercise a compatibility matrix in CI across pinned historical fixtures, currently supported releases, and a separate upstream update probe. Record whether each artifact can be identified, installed, enabled, invoked and removed. Include collision, interrupted install, upgrade, re-enable and rollback cases. Preserve pinned source and declared permissions so a failure can be traced to either an upstream change or a Qubit regression.
